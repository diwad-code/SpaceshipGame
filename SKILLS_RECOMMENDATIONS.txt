Recommended skills and MCP stack for the SpaceshipGame repository
Analysis date: 2026-05-18
Recommendation mode: COMPREHENSIVE GOOD-PLUS SET (not minimum viable)
Definition: a deliberately broader, still-coherent stack that covers design, authoring, engine workflow, UI workflow, testing, CI, and delivery support for this repo.

SOURCES REVIEWED
- SpaceshipGame repo: README, docs/ARCHITECTURE.md, docs/SCOPE.md, docs/COPILOT_WORKFLOW.md, .github/skills/*
- ComposioHQ/awesome-codex-skills: README plus selected SKILL.md files
- diwad-code/bmad-module-game-dev-studio: README, docs/reference/*, and the gds-create-game-brief / gds-gdd / gds-game-architecture / gds-investigate workflow areas
- MCP Market game-development skills catalog: https://mcpmarket.com/tools/skills/categories/game-development
- MCP Market game-development MCP catalog: https://mcpmarket.com/categories/game-development
- Additional MCP and agent-skill directories summarized in docs/skills-adoption/README.md

STARTING CONSTRAINTS
- SpaceshipGame is still in Sprint 0: there is no src/ tree and no package.json yet.
- The repo already has two local skills: scaffold-scene and scaffold-system.
- The approved stack is Phaser 4 + TypeScript + Vite + PWA + Dexie + Zod.
- Mechanics are still gated by mechanika/, so any skill or MCP must support evidence-first design instead of inventing combat, progression, or quest logic.
- We should not port BMad runtime wiring 1:1; we should adapt intent into lightweight prompts, skills, and durable docs.

SELECTION RULES USED FOR THIS LIST
1. Prefer Phaser/browser/PWA alignment over generic game-dev hype.
2. Prefer skills that help design, mechanics, documentation, scaffolding, review, or diagnostics.
3. Reject tools tightly bound to Unity, Unreal, Godot, Bevy, Minecraft plugin stacks, or unrelated automation.
4. Keep one expanded “good plus” set: broad enough to be genuinely useful, but still coherent for this repo.

1) game-brief package
   Target form:

2) gdd package
   Target form:
   - .github/prompts/gdd.prompt.md
   - docs/GDD.md
   - optionally docs/EPICS.md
   Why it belongs:

   - supports mechanics, event logic, UX, and production sequencing

4) mechanika-spec
   Target form:
   - .github/skills/mechanika-spec/SKILL.md
   Why it belongs:

   Target form:
   - .github/prompts/architecture.prompt.md or equivalent
   - docs/ARCHITECTURE.md extensions
   Why it belongs:
   - we should not stop at brief + GDD; the repo also needs a deeper technical decision layer

6) investigate package
   Target form:
   - .github/prompts/investigate.prompt.md or a lightweight skill
   Why it belongs:
   - becomes important as soon as src/, tests, workflows, and bugs appear

C) TAKE FROM ComposioHQ/awesome-codex-skills
1) skill-creator
   Why it belongs:
   - strongest bootstrap for creating and refining our own local skills
   - directly helps adapt BMad source material into .github/skills/

2) content-research-writer
   Why it belongs:

3) changelog-generator
   Why it belongs:
   - useful for release notes, milestone summaries, and visible product progress over time

4) webapp-testing
   Why it belongs:

5) gh-fix-ci
   Why it belongs:
   - high future value once GitHub Actions and validation workflows exist
   - should be ready in the target stack even if activated later

6) codebase-migrate
   Why it belongs:

   - more relevant once src/, data files, and prompt/skill assets start to multiply

D) TAKE FROM MCP MARKET SKILLS (SELECTIVELY)
The MCP Market game-development skills catalog contains many engine-specific entries. For SpaceshipGame, the strongest fits are the ones that reinforce design and browser-game thinking rather than pushing us into another engine.

1) Game Designer
   Why it belongs:
   - strongest direct fit for mechanics framing, event design, pacing, and player-facing loop quality
   - useful while mechanika/ is still becoming the source of truth

2) Gameplay Programmer
   Why it belongs:
   - good complement to our system-oriented architecture work
   - helps translate approved mechanics into clean, testable gameplay systems later

3) Level Designer
   Why it belongs:
   - relevant for beacon/map flow, event pacing, encounter distribution, and progression across sectors
   - useful even in a management game because map and encounter structure still shape the experience

4) Game Artist (later-phase support)
   Why it belongs:
   - useful once the project moves from placeholder art to more intentional UI/art direction
   - not core today, but worth including in a good-plus set instead of a minimum list

E) TAKE FROM MCP MARKET MCP SERVERS (ENGINE-ALIGNED FIRST)
1) Phaser MCP / Phaser by phaserjs
   Why it belongs:
   - most direct MCP fit for a Phaser-first project
   - useful for scene scaffolding, asset wiring, and engine-aware assistance

2) Phaser Editor MCP Server
   Why it belongs:
   - strong fit if we use Phaser Editor v5 in the workflow
   - useful for scene, asset, tilemap, and editor-assisted content flow

3) Figma MCP Server
   Why it belongs:
   - strong support for UI/UX overlays, HUD planning, responsive layout review, and design handoff
   - good match for the repo’s mobile-first and overlay-heavy UI direction

4) Blender MCP Server
   Why it belongs:
   - secondary but useful for future asset/pipeline work, mockups, and pre-rendered visual assets
   - not Phaser-specific, but still relevant to a browser game art pipeline

5) PWA Kit MCP Server (later, workflow support)
   Why it belongs:
   - not game-specific, but relevant for browser-first/PWA delivery discipline
   - useful later for installability, accessibility, and web delivery checks

SHORT DECISION
If we want a stronger non-minimum stack for this repo, the best direction is:
1. Build the design layer first: game-brief, fabula, gdd, mechanika-spec, architecture.
2. Add authoring support next: skill-creator, content-research-writer, changelog-generator.
3. Add Phaser- and UI-aligned MCPs next: Phaser MCP, Phaser Editor MCP Server, Figma MCP Server.
4. Add testing/CI/PWA delivery support as soon as the app and workflows actually exist.
5. Use docs/skills-adoption/README.md plus /skills-adoption as the autonomous adoption mechanism for executing this order.
