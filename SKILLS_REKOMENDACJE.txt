WAŻNE WNIOSKI STARTOWE
- SpaceshipGame jest nadal w Sprint 0: brak src/ i brak package.json.
- W repo gry są już dwa lokalne skills: scaffold-scene i scaffold-system.
- Z repo bmad-module-game-dev-studio nie warto przenosić runtime BMad 1:1; warto przenosić tylko sens, prompty, lekkie skille i trwałą dokumentację.
- Z awesome-codex-skills warto brać tylko rzeczy uzupełniające nasze game-specific assety, a nie dublujące obecne prompty/agentów.

==================================================
1. PRIORYTET: ADAPTACJE Z diwad-code/bmad-module-game-dev-studio
==================================================

1) game-brief package
   Docelowo: prompt + doc package, nie koniecznie czysty skill
   Po co:
   - ustala spójny brief gry przed wejściem w pełny kod
   - dobrze pasuje do obecnego etapu Sprint 0
   Docelowe miejsce:
   - .github/prompts/game-brief.prompt.md
   - docs/GAME_BRIEF.md
   Priorytet: BARDZO WYSOKI

2) gdd package
   Docelowo: prompt + doc package
   Po co:
   - porządkuje główny Game Design Document
   - daje stabilny punkt odniesienia dla późniejszych scene/system/data skills
   Docelowe miejsce:
   - .github/prompts/gdd.prompt.md
   - docs/GDD.md
   - opcjonalnie docs/EPICS.md
   Priorytet: BARDZO WYSOKI

3) mechanika-spec
   Docelowo: prawdziwy lokalny skill
   Po co:
   - idealnie pasuje do folderu mechanika/
   - pomaga dopisywać i doprecyzowywać pojedyncze specy mechanik bez rozjeżdżania reszty projektu
   Docelowe miejsce:
   - .github/skills/mechanika-spec/SKILL.md
   Priorytet: BARDZO WYSOKI

4) architecture package
   Docelowo: prompt/doc package
   Po co:
   - pogłębia decyzje architektoniczne po ustabilizowaniu briefu i GDD
   - przyda się przed większym scaffoldingiem Phaser/Vite/PWA
   Docelowe miejsce:
   - .github/prompts/architecture.prompt.md albo odpowiednik
   - docs/ARCHITECTURE.md (rozszerzenie)
   Priorytet: WYSOKI, ALE PO brief + GDD + mechanika-spec

5) investigate package
   Docelowo: lekki prompt lub skill diagnostyczny
   Po co:
   - przyda się później do badania problemów w kodzie, CI i subsystemach
   - teraz jest jeszcze za wcześnie, bo repo nie ma drzewa src/
   Docelowe miejsce:
   - .github/prompts/investigate.prompt.md lub lekki skill
   Priorytet: ŚREDNI / PÓŹNIEJ

2. PRIORYTET: SKILLS Z ComposioHQ/awesome-codex-skills
==================================================

1) skill-creator
   Dlaczego warto:
   - to najlepszy bootstrap do tworzenia i dopracowywania naszych własnych skills
   - bardzo dobrze wspiera plan przenoszenia/adaptacji assets z repo BMad do .github/skills/
   - pomaga utrzymać poprawny format SKILL.md, references/, scripts/ i assets/
   Priorytet: BARDZO WYSOKI
   Wniosek: BRAĆ

2) webapp-testing
   Dlaczego warto:
   - po pojawieniu się Vite/Phaser/PWA da nam sensowny workflow do testów UI i regresji
   - dobrze pasuje do przyszłych scen, overlayów HTML/CSS i testów PWA
   Priorytet: WYSOKI, ALE DOPIERO PO SCAFFOLDZIE APLIKACJI
   Wniosek: BRAĆ PÓŹNIEJ

3) gh-fix-ci
   Dlaczego warto:
   - po wejściu workflowów GitHub Actions ułatwi diagnozę i naprawę CI
   - dobrze pasuje do przyszłych build/test/PWA checks
   Priorytet: WYSOKI, ALE DOPIERO GDY BĘDZIE CI
   Wniosek: BRAĆ PÓŹNIEJ

4) changelog-generator
   Dlaczego warto:
   - przyda się do release notes dla PWA/Android i do czytelnych zmian produktowych
   - dobrze wspiera utrzymywanie changelogów i podsumowań wersji
   Priorytet: ŚREDNI/WYSOKI
   Wniosek: BRAĆ

5) codebase-migrate
   Dlaczego warto:
   - będzie pomocny dopiero przy większych migracjach i masowych refaktorach
   - dziś repo jest zbyt małe, ale później może być przydatny przy większej reorganizacji scen/systemów/data
   Priorytet: ŚREDNI / PÓŹNIEJ
   Wniosek: BRAĆ TYLKO GDY REPO UROŚNIE

6) content-research-writer
   Dlaczego warto:
   - może pomóc przy większych paczkach dokumentacji: GAME_BRIEF, GDD, mechanika, ADR-y
   - ma sens głównie do długich, researchowych dokumentów
   Priorytet: ŚREDNI
   Wniosek: OPCJONALNIE
